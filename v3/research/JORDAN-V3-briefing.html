JORDAN V3 Briefing

JORDAN turns planning doctrine and problem-solving methods into a workflow for AI coding agents. This page shows what new research says about version 2, and the shape it proposes for version 3.

What moves outcomes

Where effort pays, strongest first

The July review ranked harness over routing over isolation over prompt. The new evidence keeps the spirit and corrects the order. This is a ranking by strength of evidence. The steps are not drawn to a measured scale.

  1. Checks and loss prevention in the harnessProtected tests, an exit for impossible tasks, recovery when a run is cut off.v2 called this "harness enforcement" and ranked it first. Still first.
  2. Which model does the core workModel generation changes capability far more than any scaffold.New to the ranking.
  3. Context disciplineA small always-on file and focused context. Isolation for parallel breadth.v2 ranked isolation third. Holds.
  4. Routing work to cheaper modelsSaves money. Its effect on quality is small and only vendor-measured.v2 ranked this second. Moves down.
  5. Process written into promptsPhases, personas, planning prose, self-review. Paid for again on every step.Includes elaborate harness process, which v2 counted under rank one.
The proposed workflow

One route, two lanes, three human posts

Follow the line down. At each stop the model uses judgment, and the harness enforces whatever a script can check. The person appears at three posts only.

The model judges The harness enforces in code The person decides
The model judgesThe harness enforces
1

Take the intent

Ask questions only when the request is underspecified, in one batch, with a proposed default for each. Write down the request and one other way to read it.

Nothing to enforce yet
Human post 1

Sign off the intent and what "done" means. The cheapest place to correct a wrong direction.

2

Size it up

Fast, standard or deep. Two extra questions: is there a quick check that can be trusted, and does the task mix untrusted input, sensitive access and outside effects?

In code
  • A preflight refuses to start outside a sandbox when credentials are exposed.
  • A role that holds all three risky properties is refused.
3

Wire the check first

Decide how success will be shown before any work: which kind of check fits, and who writes it. Treat a fix suggested in the request as a guess. If the task is impossible or contradicts itself, say so and stop.

In code
  • Existing tests and acceptance commands become read-only to the builder.
  • Edits that delete tests, add skips or loosen thresholds are rejected.
4

Plan the next wave only

List the acceptance checks, a thin end-to-end slice to build first, and the assumptions the plan rests on. Name the one observation that would prove the plan's premise wrong. Later waves stay as one-line milestones.

In code
  • The plan file must contain its checks, owners and assumptions.
  • Each assumption needs a command that tests it, or it is logged as a named risk.
5

Try it, in a tight loop

Attempt the whole unit against its check. Act, run the check, read the real output, correct. Split the work only when the check fails. Fan out to other agents only for independent, read-heavy work.

In code
  • A worker restates its task before its first edit, and the restatement is compared with the brief.
  • Budgets for cost, time and tool calls. A repeated identical call is caught.
  • Deletes, credential reads and unknown package installs are blocked.
If a planned trigger appearsRun the branch

The plan already said what to do. No new planning.

If something unforeseen happensAdjust once

Diagnose with written predictions, form one workable option, continue.

If the premise is wrongAbandon and re-size

Stop patching. Say what the evidence shows and return to stop 2.

Human post 2, only when needed

Approve an action that cannot be undone. Pushing to the main branch, deleting outside the workspace, changing infrastructure, spending, sending anything outside.

6

Independent review

A reviewer in a fresh context writes what it expects from the specification alone, then reads the change. Its verdict must quote a command it ran. Opinions without a command are discarded.

In code
  • The reviewer has read-only tools.
  • Its verdict has a fixed form: refuted, not refuted, or cannot verify.
7

Prove it is done

Report two things separately: the task finished, and the outcome the person wanted is met. State what kind of evidence each claim rests on.

In code
  • The session cannot end as "done" until the evidence commands re-run and pass.
  • A bug fix needs a recorded failing run before the fix and a passing run after.
Human post 3

Review the package. Purpose, commands run with their output, risk level, decisions made, and a recommendation.

8

Learn in code

Ask what was expected, what happened, and why they differ. Then name the file, hook or test that will change, and the check that shows the change worked.

In code
  • A lesson that names no file, hook or test is not filed.
  • The check that should have caught the problem is added as a test.

Done, with evidence

Inside stop 5

The loop, and the diagnosis that guards it

When the check fails, diagnose before fixing again

Version 2 gave diagnosis one line. The research found agents repair a fault more often than they identify it, so version 3 gives it a short written procedure:

1. Reproduce the failure and paste the output.
2. Find a similar case that passes.
3. List candidate causes, and for each one write what it predicts that the others do not.
4. Run the test where the predictions differ.
5. Confirm the cause both ways: remove it and the fault goes, force it and the fault returns.

More agents is a choice

Fan out for breadth, not for chains

A controlled 2025 study compared agent team shapes at equal token budgets. It had no coding benchmark, so read it as direction. Most coding work is the left-hand kind.

Dependent steps, one after another
39 to 70% worse

Every multi-agent shape tested did worse than one agent on sequential planning. Keep a dependent chain in one thread.

Independent pieces, checked centrally
80.8% better

A central coordinator on a task that splits cleanly. Unchecked merging multiplied errors 17.2 times, against 4.4 times with a central check.

How strong is the proof

The evidence ladder for "done"

Every completion report says which rung it stands on, and whether the builder could have edited the check.

Something ran and the result is quotedA test, a command, a rendered screen. Stronger when the builder did not write the check.
A reviewer from a different model family, or a stronger modelFewer shared blind spots.
A fresh-context reviewer from the same familyRemoves context contamination, keeps the shared blind spots.
The builder's own say-soWorth nothing alone.
Running with prompts switched off

Safety comes from layers around the agent

The operator runs agents without permission prompts. That is defensible only when what the agent cannot reach is set by its surroundings.

BoundaryA sandbox limited to the working folder, an allowlist for outside connections, short-lived credentials, backups the agent cannot touch.
Hard blocksScripts that refuse risky deletes, credential reads, forced pushes, unknown packages, and edits to tests or to the hooks themselves.
Role limitsNo single agent may read untrusted content, hold sensitive access and act on the outside world all at once.
UndoA separate working copy per task, checkpoints, dry runs, and a human signature for the few actions with no undo.
The agent, working under budgets for cost, time and tool calls, with every tool call written to a trace.

How far to trust this

What the research did and did not check

Read at the source

The agent studies, vendor engineering posts, Claude Code documentation and several Army articles were opened and read during the research.

Recalled, not re-read

Most military doctrine definitions and the classic texts come from model memory. A shared page-reading budget ran out. Check them before quoting.

Not tested anywhere

No study has measured premortems, confirmation briefs or intent statements on coding agents. The test suite is how JORDAN finds out.
