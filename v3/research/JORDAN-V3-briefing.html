JORDAN V3 Briefing

JORDAN turns planning doctrine and problem-solving methods into a workflow for AI coding agents. This page shows what new research says about version 2, and the design of version 3 that came out of it.

Verify in codeChecks the agent cannot edit, enforced by hooks, decide when work is done.
Say less in promptsA small plain kernel. Process that a hook can enforce leaves the prompt.
Measure everythingNo phase stays unless a test against a plain agent shows it earns its cost.

The workflow below is the settled version 3 design, now being built. Details may still move during the build. Figures come from the research report, which names the source for each.

What moves outcomes

Where effort pays, strongest first

The July review ranked harness over routing over isolation over prompt. The new evidence keeps the spirit and corrects the order. This is a ranking by strength of evidence. The steps are not drawn to a measured scale.

  1. Checks and loss prevention in the harnessProtected tests, an exit for impossible tasks, recovery when a run is cut off.v2 called this "harness enforcement" and ranked it first. Still first.
  2. Which model does the core workModel generation changes capability far more than any scaffold.New to the ranking.
  3. Context disciplineA small always-on file and focused context. Isolation for parallel breadth.v2 ranked isolation third. Holds.
  4. Routing work to cheaper modelsSaves money. Its effect on quality is small and only vendor-measured.v2 ranked this second. Moves down.
  5. Process written into promptsPhases, personas, planning prose, self-review. Paid for again on every step.Includes elaborate harness process, which v2 counted under rank one.
The version 3 workflow

One route, nine rules, one human post

Follow the line down. The kernel is nine short rules the agent always carries. Hooks enforce what a script can check. Seven modules stay on the shelf until a trigger calls for one. The person is asked only before an action that cannot be undone.

1
Rule 1

Size the task

One sentence: fast (one step, easy to undo), standard (several steps) or deep (hard to undo). Unsure whether it can be undone, pick the higher. Unsure only how hard it is, pick the lower and move up at the first surprise.

Session start
  • The kernel is placed in the agent's context when the session opens, so the rules are present without being asked for.
2
Rule 2

Name the check

Before starting, name the command or observation that will show the work is right, and record it. If no check exists, build it first. If none can exist, say so and label the result unverified.

verifywhen no existing test covers the change
The ledger
  • Records the check command, the starting commit and the protected test paths.
  • Kept outside the workspace, where the agent's edits do not reach it.
3
Rule 3

Try the direct route

Attempt the work as one piece. Split it only when a check fails or it must run in parallel. Plan only the next step in detail.

planwhen the direct attempt failed its check, or the step is hard to undosplitwhen a check failed, or parallel work is on the table
Nothing to enforce here
4
Rules 4, 5 and 9

Work the loop

Act, run the check, read the actual output, correct. Every retry changes something that can be named. Leave existing tests alone. Make the smallest change that meets the request.

diagnosewhen the cause is unclear, or a fix did not workrecoverat the first failed check after a correction
Trace and early notice
  • Every tool call is written to a trace. It never blocks.
  • An edit to a protected test is refused on the spot, with the reason.
The check passesCarry on to the report

Nothing else is required.

The check failsCorrect and go round again

After two attempts that each made things worse, stop and rebuild the diagnosis from the raw output.

Rule 6: the premise is wrongDrop the plan

Say what the evidence shows and return to stop 1.

Rule 5: it cannot be done as writtenStop and report that

The checks contradict the request. Saying so is a correct result.

Rule 7, the human post

Get a decision before an action that cannot be undone. Deleting outside the workspace, force-pushing, publishing, spending, changing infrastructure, sending anything outside the session. If no one is reachable, the agent returns a decision request and stops.

briefto write the decision requestoptionswhen the step is hard to undo and alternatives are worth comparing

In code: a guard on shell commands catches recursive deletes outside the workspace, forced pushes and publishing. It catches accidents. It is not a sandbox.

5
Rule 8

Report with evidence

Quote the check's output. Say separately whether the outcome asked for is met. Say "implemented but unverified" when the check did not run. Give only numbers a tool produced or that were counted.

The done-gate
  • Before the agent may stop, the recorded check runs again.
  • The changes are compared with the starting commit for edits to protected tests.
  • A failing check blocks the stop once and shows the output. A timeout is reported as unverified. There is no silent pass.

The loop, and the diagnosis that guards it

When the check fails, diagnose before fixing again

Version 2 gave diagnosis one line. The research found agents repair a fault more often than they identify it, so version 3 gives it a module of its own:

1. Reproduce the failure and paste the output.
2. Find a similar case that passes.
3. List candidate causes, and for each one write what it predicts that the others do not.
4. Run the test where the predictions differ.
5. Confirm the cause both ways: remove it and the fault goes, force it and the fault returns.

More agents is a choice

Fan out for breadth, not for chains

A controlled 2025 study compared agent team shapes at equal token budgets. It had no coding benchmark, so read it as direction. Most coding work is the left-hand kind.

Dependent steps, one after another
39 to 70% worse

Every multi-agent shape tested did worse than one agent on sequential planning. Keep a dependent chain in one thread.

Independent pieces, checked centrally
80.8% better

A central coordinator on a task that splits cleanly. Unchecked merging multiplied errors 17.2 times, against 4.4 times with a central check.

Running with prompts switched off

Safety comes from layers around the agent

The operator runs agents without permission prompts. That is defensible only when what the agent cannot reach is set by its surroundings. Version 3.0 ships the guard and the done-gate, which catch accidents. The outer layers below are the research recommendation and are yours to set up.

BoundaryA sandbox limited to the working folder, an allowlist for outside connections, short-lived credentials, backups the agent cannot touch.
Hard blocksScripts that refuse risky deletes, credential reads, forced pushes, unknown packages, and edits to tests or to the hooks themselves.
Role limitsNo single agent may read untrusted content, hold sensitive access and act on the outside world all at once.
UndoA separate working copy per task, checkpoints, dry runs, and a human signature for the few actions with no undo.
The agent, working under budgets for cost, time and tool calls, with every tool call written to a trace.

How far to trust this

What the research did and did not check

Read at the source

The agent studies, vendor engineering posts, Claude Code documentation and several Army articles were opened and read during the research.

Recalled, not re-read

Most military doctrine definitions and the classic texts come from model memory. A shared page-reading budget ran out. Check them before quoting.

Not tested anywhere

No study has measured premortems, confirmation briefs or intent statements on coding agents. The test suite is how JORDAN finds out.
