# Lane F: Current industry practice for AI coding agent workflows (2025 to November 2026)

Method note. Page reads were limited by a shared fetch budget (100 per hour across all lanes) that ran out repeatedly. Items marked [verified] were read on a page this session. Items marked [recalled] come from training memory and were not re-opened. Where a search returned only a title and URL, I say so under Gaps. Nothing here is a number I did not read on a source.

## Summary (the findings that matter most)

1. **The vendor consensus is "harness enforcement over prompt content", in Anthropic's own words.** Claude Code's best-practices page says a prompt, CLAUDE.md or skill is "non-deterministic" and that a rule with zero exceptions belongs in a hook, deny rule or managed setting. It says that if you keep adding emphasis to a CLAUDE.md line, the line belongs in a hook. This validates JORDAN's internal review conclusion and contradicts v2's reliance on a prompt-simulated 12-phase pipeline. [verified]
2. **Anthropic now publishes a "what you can stop doing" table.** Managing context aggressively, ALL-CAPS emphasis, "think hard", "loop until done", subagents to protect context, and describing architecture in CLAUDE.md are all listed as obsolete for current models. v2's kernel and CLAUDE.md use several of these habits. [verified]
3. **Instruction files should be short, and LLM-generated ones hurt.** An ICLR-2026 paper measured that LLM-generated context files lowered success by about 3% on average and raised cost by over 20%, and that human-written files helped by about 4% (not for Claude Code) at up to 19% more cost. Claude Code docs recommend under 200 lines; OpenAI keeps AGENTS.md at about 100 lines as a table of contents. [verified]
4. **Multi-agent setups pay off only in narrow shapes.** Cognition's 2026 revision and Anthropic's research-system post agree: single writer, extra agents that contribute intelligence (review, escalation, research), clean-context reviewer. Parallel writer swarms and agent negotiation are still reported as failures. v2's "premium lead decides, cheap models build, fresh-context refuters verify" matches the surviving shape. [verified]
5. **Every scaffold in a harness should be treated as a hypothesis about model weakness.** Anthropic's harness-design post removed sprints, then per-sprint evaluation, as Opus 4.6 improved, kept the planner, and kept the evaluator as conditional. V3 needs an ablation habit that v2 lacks. [verified]
6. **Long-running work uses external files with machine-checkable state.** Anthropic's feature-list JSON with a `passes` flag, a progress file, `init.sh`, and clean-state commits; OpenAI's four files (prompt.md, plans.md, implement.md, documentation.md); the Codex ExecPlan. v2 has handoff files but no structured, tamper-resistant feature ledger. [verified]
7. **A separate evaluator agent is useful but must be tuned, and is costly.** Anthropic measured roughly 20x cost for the full harness versus a solo run on one task and says the evaluator still leans lenient. Fresh-context review has independent supporting evidence from Cognition (Devin Review). [verified]
8. **The review bottleneck is the dominant 2026 problem.** Practitioners respond with risk-tiered review, intake bars on agent PRs, heterogeneous AI reviewers, and treating AI review as a sensor. v2 has no PR-volume or review-capacity design. [verified via Osmani's survey; the underlying vendor statistics are vendor-sourced]
9. **Claude Code now exposes enough enforcement points to build most of JORDAN's gates in code.** 30+ hook events (Stop, SubagentStop, TaskCompleted, TeammateIdle, PreToolUse with `updatedInput`, PostToolBatch, PreCompact), hook types including `prompt` and `agent`, `onFailure: "block"`, `/goal`, subagent frontmatter (tools, model, hooks, isolation worktree, memory, maxTurns), and permission modes. [verified]
10. **Spec-driven development is widely adopted and weakly evidenced.** Fowler/Thoughtworks's hands-on review found Kiro and spec-kit heavy for small tasks and non-deterministic at the code level. The Ralph loop sits in Thoughtworks's Assess ring (April 2026) and is no longer on the current radar. [verified]

## Findings

### F1. Claude Code's enforcement surface (what a V3 can hook into)
**What it is.** Claude Code is configured by `settings.json`, hooks, subagent files, skills, plugins, and permission modes. The hook list below is from the hooks reference, read up to its truncation point (the final ~9.5k characters of the page were not read). [verified: https://code.claude.com/docs/en/hooks]
- **Events** (can-block in brackets): SessionStart, Setup, UserPromptSubmit [yes], UserPromptExpansion [yes], PreToolUse [yes], PermissionRequest [via decision object], PermissionDenied (can set `retry`), PostToolUse, PostToolUseFailure, PostToolBatch [yes, stops the loop], Notification, MessageDisplay, SubagentStart, SubagentStop [yes], TaskCreated [yes], TaskCompleted [yes], Stop [yes], StopFailure, TeammateIdle [yes], InstructionsLoaded, ConfigChange [yes], CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate [yes], WorktreeRemove, PreCompact [yes], PostCompact, PreModelSwitch [yes], PostModelSwitch, Elicitation [yes], ElicitationResult [yes], SessionEnd.
- **Hook types**: `command`, `http`, `mcp_tool`, `prompt` (a model returns a decision; 30 s default), `agent` (spawns a read-only-tool subagent to verify a condition; experimental; 60 s default). The best-practices page states plainly that `prompt` and `agent` hooks "aren't deterministic either."
- **Control channel**: exit code 2 blocks and returns stderr as the reason; JSON output supports `decision: "block"`, `permissionDecision` (allow/deny/ask/defer), `updatedInput` (rewrite tool args before execution), `updatedToolOutput`, `additionalContext` (injects a system reminder), `continue: false`. `onFailure: "block"` (v2.1.295+) makes a crashed or timed-out hook fail closed; without it, a timed-out PreToolUse hook does not block.
- **Stop hook ceiling**: a Stop hook that blocks eight times in a row with no tool call between is overridden; the cap is raisable with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. [verified: best-practices page]. This is the harness's own version of JORDAN's "ceilings with flags".
- **`/goal <condition>`**: a separate model checks the condition against the conversation after every turn and sends Claude back to work until it is met. Intended for unattended runs. [verified]
- **Subagent files** (`.claude/agents/*.md`): frontmatter `tools`/`disallowedTools` (enforced by the harness, so a `Read, Grep, Glob` reviewer cannot edit), `model` (sonnet, opus, haiku, fable, full ID, inherit), `permissionMode`, `maxTurns`, `skills` (preloaded), `hooks` (scoped to that subagent), `memory` (user/project/local persistent directory; first 200 lines or 25KB of MEMORY.md loaded), `isolation: worktree`, `effort`, `omitClaudeMd`, `background`. Model resolution order: per-call parameter, then definition, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the main model; `..._FORCE=1` overrides definitions. Nesting defaults to three layers (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`); concurrency caps at 20 by default. Descriptions share a 15,000-token startup budget. [verified: https://code.claude.com/docs/en/sub-agents]
- **Agent teams** (experimental, off by default, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`): lead plus teammates, shared task list with dependencies and file-locked claiming, mailbox JSON files, hooks TeammateIdle/TaskCreated/TaskCompleted for quality gates, plan-approval requests. Limits: no session resumption for in-process teammates, one team per session, no nested teams, task status can lag. Docs recommend 3 to 5 teammates and 5 to 6 tasks each, say the strongest uses are research, review, competing-hypothesis debugging and separately owned modules, and warn that sequential work and same-file edits are better served by a single session or subagents. [verified: https://code.claude.com/docs/en/agent-teams]
- **Other surfaces named in the docs**: auto mode (a classifier approves or blocks actions; interactive sessions start in it), `/code-review` (fresh-context subagent reviewing a diff), `/batch` (splits a mechanical change into 5 to 30 units, one worktree and PR each), worktrees (`claude -w`, `.worktreeinclude`), checkpoints and `/rewind` (cover only edits made with Claude's file tools, not Bash side effects), `--bare` headless mode (skips hooks, skills, CLAUDE.md), `claude agents` background view (research preview), `/doctor prompt-audit` (flags instructions written for older models, dead file references and contradictions). [verified: best-practices page]
**Critique.** Hooks are only deterministic if they are `command`/`http` type and set to fail closed; hooks are repo-level and run only after workspace trust; teams are explicitly experimental; auto mode is a model, not a rule (see F2).
**Transfer.** Almost every v2 gate has a hook home: CLASSIFY and INTENT intake on UserPromptSubmit/UserPromptExpansion; "done-claim must quote evidence" on Stop (exit 2 with the missing-evidence message); acceptance commands on TaskCompleted/SubagentStop; fences on PreToolUse deny; context preservation on PreCompact/PostCompact (re-inject goal, constraints, state via `additionalContext`); branching monitor on SubagentStart (count, depth).
**V3 implication.** V3 should move every "MANDATORY" gate that has a mechanically checkable condition into `command` hooks with `onFailure: "block"` and keep only the judgement parts in prompts, because the vendor's own guidance says prompt-level rules are advisory. Belongs in harness code. Also V3 should ship a `/doctor prompt-audit`-style check for stale instructions into the eval suite.

### F2. Auto mode and containment (Anthropic, 2026)
**What it is.** Two layers: a server-side prompt-injection probe on tool outputs, and a transcript classifier (Sonnet 4.6) that reviews each action before it runs in two stages (fast yes/no filter, then reasoning on flagged items). It sees user messages and tool calls only, not assistant prose or tool results. Read-only tools and in-project edits skip it. Users were reported to approve 93% of permission prompts, the motivation. [verified: https://anthropic.com/engineering/claude-code-auto-mode]
**Evidence.** Full pipeline false-positive rate 0.4% on 10,000 real tool calls; false-negative rate 17% on 52 real "overeager" actions and 5.7% on 1,000 synthetic exfiltration cases. The authors call 17% "the honest number" and say it is not a replacement for human review on high-stakes infrastructure. Blocks escalate to a human after 3 consecutive or 20 total denials. [verified]
**Critique.** Small real test set (52) and synthetic exfiltration data; most misses come from treating a loose approval as consent for the whole action. Also listed in the Claude Code docs: deny rules and PreToolUse hooks run before the classifier, so "never" rules belong there. [verified]
**Transfer.** The design of the classifier (sees only user intent and actions, not the agent's rationalisation) is a transferable principle: a verifier that cannot read the actor's reasoning is harder to talk round.
**V3 implication.** V3's default-deny safety should be expressed as deny rules and PreToolUse hooks, with auto mode treated as a second layer and not as the guard; and any V3 "independent verifier" should be given artifacts (diff, spec, commands) and not the author's reasoning. Belongs in harness code and orchestration.

### F3. Anthropic "Claude Code best practices": the model of how a session should run
**What it is.** The current page (read in full via a saved copy) organises advice around four ideas: tell Claude what it cannot see; give it a check to run; enforce rules that cannot have exceptions; manage cost and parallelism. Specific mechanics: a verify step is the highest-leverage input (tests, typecheck, Stop hook, `/goal`, fresh-subagent `/code-review`); write a SPEC.md in one session and build from it in a fresh session; keep CLAUDE.md to what Claude cannot infer from code (commands, misleading places, off-repo decisions, anything corrected twice) and "stay under 200" lines; use skills for procedures because only name and description are always loaded; give a review subagent only read tools; prompt reviewers to "skip style" because a reviewer asked to find problems always finds something. [verified: https://code.claude.com/docs/en/best-practices]
**What to stop doing (verbatim categories).** Manage context aggressively (1M windows and auto-compaction make running out rare, but `/clear` between tasks still helps); IMPORTANT/ALL CAPS (over-applied by current models); subagents purely to protect context; delegating "for a better answer" (a fresh reviewer helps, delegation alone does not); `think hard` phrases (effort setting is the control); "keep going, loop until done, don't be lazy" (causes over-work); describing architecture in CLAUDE.md. [verified]
**Critique.** This is a vendor page; it asserts rather than measures. The only measured items are in the separate studies cited in F4 and F11.
**Transfer.** The "reviewer finds something always" warning applies directly to v2's refuters and premortems: they need an exit criterion ("only report what breaks acceptance criteria") or they will inflate scope.
**V3 implication.** V3 should add a scope-limiter to every verifier and premortem prompt ("report only defects that violate acceptance criteria; skip style") because the vendor documents reviewer over-reporting; kernel-level. Contradiction flag: v2's "MANDATORY", "Rule", and persona-heavy premortem language runs against the "plainly worded line" advice.

### F4. Instruction files: size, content, and evidence
**What it is.** Evidence and recommendations for AGENTS.md / CLAUDE.md.
- Measured: "Evaluating AGENTS.md" (ICLR 2026) tested Claude Code with Sonnet 4.5, Codex with GPT-5.2 and GPT-5.1 mini, and Qwen Code on SWE-bench Lite (300 tasks) and a new AGENTbench (138 instances, 12 repos with developer-written files). Developer-written files improved success by about 4% on average (not for Claude Code). LLM-generated files lowered success by about 3% on average (breakdown in the paper: 0.5% on SWE-bench Lite, 2% on AGENTbench; the paper's own sections differ) and raised cost about 20 to 23% (about 2.5 to 3.9 extra steps). Agents obey the files (a tool named in the file was used about 1.6 times per instance versus under 0.01 when absent), but the files did not make agents reach the right files sooner. LLM-generated files mostly duplicated existing docs. Authors' recommendation: omit LLM-generated context files and keep human-written ones to minimal requirements such as specific tooling. [verified: https://arxiv.org/abs/2602.11988 and https://arxiv.org/html/2602.11988v1]
- OpenAI harness engineering: a single large AGENTS.md failed (crowds out the task, rots, cannot be mechanically verified); they kept it to roughly 100 lines as a map into a `docs/` tree, plus linters/CI that check the docs are current and cross-linked. [verified: https://openai.com/index/harness-engineering/]
- Claude Code docs: under 200 lines; personal preferences in `CLAUDE.local.md`; scope rules per directory with `.claude/rules`; `/init` output should be pruned. [verified]
**Critique.** The ICLR study uses Python benchmark tasks with short horizons and no evidence on long-running work; the 4% figure excludes Claude Code, which is the host V3 targets.
**Transfer.** The best-supported content is commands and tooling the agent cannot guess; architecture summaries and generated overviews do not earn their cost.
**V3 implication.** V3 should keep the always-on kernel to commands-and-rules the agent cannot infer, ideally at or below the current ~500 tokens, move anything procedural into skills, and measure kernel on/off in the eval suite, because the only controlled evidence says instruction files cost 19 to 23% more and help little. Belongs in the kernel and the eval suite. JORDAN's own CLAUDE.md (long, with a 19-item maxim list) is the thing this evidence argues against.

### F5. Anthropic long-running harnesses: initializer, feature list, progress file
**What it is.** A two-part harness for the Agent SDK. A first "initializer" session creates `init.sh` (starts the dev server), a progress log, an initial git commit, and a JSON feature list where each feature has a description, test steps, and a `passes` flag starting false. Later coding sessions each: read the working directory, progress notes, git log and feature list; run `init.sh` and a basic end-to-end test; pick one unfinished feature; test it as a user would (browser automation, because unit tests and curl missed broken features); flip only the `passes` flag; commit and update notes, leaving the tree mergeable. JSON was chosen because models overwrite JSON less readily than Markdown. [verified: https://anthropic.com/engineering/effective-harnesses-for-long-running-agents]
**Evidence.** Qualitative; the post includes a failure-mode table (declares done too early, leaves bugs, marks features done prematurely, wastes time on setup) mapped to the fix for each. It lists open questions (whether specialised QA agents beat one generalist; transfer beyond web apps). No benchmark.
**Critique.** The post is about greenfield app builds; "one feature per session" assumes small, separable features.
**Transfer.** The pattern generalises: state lives in files with a schema, edit rights on the verdict field are restricted, and every session starts with an orientation protocol.
**V3 implication.** V3 should replace free-form handoff notes with a JSON ledger (subtask id, acceptance command, `passes`, evidence path) whose `passes` field can only be written by a hook that ran the acceptance command, because Anthropic found agents mark work done prematurely. Belongs in harness code (a PostToolUse/TaskCompleted hook plus a schema) and the orchestration layer.

### F6. Anthropic planner/generator/evaluator harness and the "remove scaffolding" lesson (2026)
**What it is.** A GAN-inspired three-agent harness for application building. The planner expands a 1 to 4 sentence prompt into a deliberately high-level spec. The generator builds in sprints. The evaluator drives the live app with Playwright, scores against criteria with hard thresholds, and fails the sprint if any criterion is below its threshold. Before each sprint the generator and evaluator agree a "sprint contract" (what will be built and how success will be verified) through files. Evaluator calibration used few-shot scored examples and several rounds of reading its logs and editing its prompt. [verified: https://www.anthropic.com/engineering/harness-design-long-running-apps]
**Evidence (single author, a few prompts, not a controlled benchmark).** Retro game maker: solo run 20 minutes and $9 produced a game whose core did not respond to input; full harness 6 hours and $200 produced a working 16-feature result. DAW build with Opus 4.6 and the simplified harness: about 3 h 50 min and $124.70, with QA rounds catching real gaps. With Sonnet 4.5 the harness needed context resets because of "context anxiety"; with Opus 4.5 that disappeared and resets were dropped; with Opus 4.6 the sprint construct and per-sprint evaluation were removed (evaluator moved to one end pass), the planner was kept.
**Critique.** The author's own caveats: roughly 20x cost, slow, evaluator still lenient and superficial on deeply nested features, results short of professional quality, later iterations not monotonically better.
**Transfer.** The sprint contract is the backbrief in artifact form: executor restates, evaluator agrees, tests are fixed before work. The ablation method (remove components one at a time and see what is load-bearing) is directly transferable.
**V3 implication.** V3 should (a) require a written, evaluator-agreed acceptance contract before any DEEP subtask starts (v2's pointer briefs with acceptance commands are close), and (b) put every pipeline phase on an ablation schedule in the eval suite, retiring phases that do not change outcomes on the current model, because Anthropic's own harness shrank as models improved. Belongs in orchestration and the eval suite. Flag: v2's 12 phases are fixed; the evidence here says phase count should be model-conditional.

### F7. Anthropic multi-agent research system, and where multi-agent pays
**What it is.** Orchestrator-worker: a lead plans, saves the plan to memory (context past 200k tokens is truncated), spawns subagents with their own windows and tools that return condensed findings, and a separate CitationAgent attributes claims. Eight prompting principles, notably: give each subagent objective, output format, tool guidance and task boundaries (vague briefs caused duplicated work); scale effort to complexity with explicit rules in the prompt (1 agent and 3 to 10 tool calls for simple queries, up to 10+ subagents for complex); let models rewrite their own tool descriptions. [verified: https://www.anthropic.com/engineering/multi-agent-research-system]
**Evidence.** On Anthropic's internal research eval an Opus 4 lead with Sonnet 4 subagents beat single-agent Opus 4 by 90.2%. On BrowseComp token usage alone explained 80% of performance variance. Agents use about 4x the tokens of chat, multi-agent about 15x. The post lists failure modes (50 subagents for a simple query, endless search for nonexistent sources, duplicated searches) and says multi-agent is a poor fit where agents must share context, where dependencies are heavy, and for "most coding tasks." About 20 queries sufficed for an initial eval set; end-state evaluation is advised for stateful tasks.
**Critique.** The 90.2% figure is on an internal research eval; token spend is a confound the post itself identifies (80% of variance).
**Transfer.** The brief format maps onto v2's pointer briefs. "Scale effort to complexity, written into the prompt" matches v2's FAST/STANDARD/DEEP.
**V3 implication.** V3 should state the multi-agent budget rule in the kernel (default single agent; fan-out only for breadth-first read-only work; coding writes stay single-threaded) and log token spend per task in the eval harness so that "multi-agent helped" is separated from "more tokens helped". Kernel plus eval suite.

### F8. Cognition (Devin): from "Don't Build Multi-Agents" to "What's Actually Working"
**What it is.** The 2025 post argued that agents must share full context and that parallel agents make conflicting implicit decisions. [recalled; the post URL appeared in search results at https://cognition.com/blog/dont-build-multi-agents but was not read]. The 2026 follow-up reads: multi-agent works when writes stay single-threaded and extra agents contribute intelligence rather than actions. [verified: https://cognition.com/blog/multi-agents-working]
- **Generator-verifier review loop.** Devin Review reportedly catches on average 2 bugs per PR, about 58% severe (Cognition's own number, vendor-reported). Works best with a clean-context reviewer that shares nothing with the coder; reasoning: shared bias comes from training and not ego, long contexts rot, and a reviewer without the spec can question instructions the coder accepted. Findings are filtered through the coder side's knowledge of user intent to stop endless loops and scope creep.
- **"Smart friend" escalation.** A cheap fast primary model calls a stronger model as a tool: force at least one call, force escalation on domain triggers (merge conflicts), share a fork of the full context, ask broad questions, let the smart model over-scope. A much weaker primary did not work (it could not judge when to escalate). Across frontier models it works as a capability router.
- **Manager-child delegation** in production: failure modes were over-prescribing managers, assumed shared state, and children not reporting back; preferred shape is "map-reduce-and-manage."
- **Does not work**: parallel-writer swarms and unstructured agent networks ("mostly a distraction").
**Critique.** Vendor-authored with vendor metrics; no independent replication.
**Transfer.** Strong match to v2's shape (premium lead rules, cheap builders, fresh refuter). The "weak primary cannot know when to escalate" finding warns against v2's assumption that cheap models will self-escalate.
**V3 implication.** V3 should make escalation to the strong model a hook- or rule-triggered event for named conditions (merge conflict, failed acceptance twice, safety flag) and not rely on the cheap builder's judgement, because Cognition found weak primaries misjudge when to escalate. Orchestration plus harness. Also V3 should keep writes single-threaded per file set (fences) and parallelise only read-only work and independent worktrees.

### F9. OpenAI harness engineering, long-horizon Codex, PLANS.md
**What it is.** (a) OpenAI's team shipped an internal beta with zero hand-written code over five months, about 1,500 merged PRs and about a million lines, with 3 to 7 engineers; engineers design environments and feedback loops ("Humans steer. Agents execute."). Mechanisms: AGENTS.md as a roughly 100-line map into versioned `docs/`; the repo as the only system of record; apps bootable per git worktree with browser DevTools and a local observability stack the agent can query; a fixed layered architecture enforced by custom linters and structural tests whose error messages carry remediation instructions; "golden principles" plus background agents that scan for drift and open small refactoring PRs; agent-to-agent review with minimal merge gates. [verified: https://openai.com/index/harness-engineering/]
(b) The long-horizon Codex post: four durable files (prompt.md as spec with goals, non-goals, constraints and a "done when"; plans.md with milestones each having acceptance criteria and validation commands and a stop-and-fix rule; implement.md as the runbook; documentation.md as status/decision log). One run lasted about 25 hours, used about 13M tokens, and produced about 30k lines, described by the author as "not perfect or production-ready." [verified: https://developers.openai.com/blog/run-long-horizon-tasks-with-codex]. The ExecPlan / PLANS.md cookbook article exists at https://developers.openai.com/cookbook/articles/codex_exec_plans (title and URL from search only; not read).
**Evidence and critique.** Numbers are OpenAI-reported on its own project. Failures stated: early progress slow because the environment was underspecified; monolithic AGENTS.md failed; agents replicate bad patterns (entropy), so cleanup became automated; human QA became the bottleneck; long-term architectural coherence unknown; the approach "depended heavily on this repo's tooling." They also say minimal merge gates "would be irresponsible at lower throughput."
**Transfer.** Lint errors that tell the agent how to fix them are a cheap, high-yield pattern (the agent reads the tool output verbatim, which is v2's micro-loop). The stop-and-fix rule equals v2's "never rerun unchanged".
**V3 implication.** V3 should add a drift-control practice: custom lint/structural tests with remediation messages generated from the project's own rules, and an optional scheduled "garbage collection" task, because OpenAI reports agents copy existing bad patterns. Harness code plus an on-demand module. V3's plan format should be convertible to the plans.md shape (milestones, acceptance, validation commands, decision log) so JORDAN plans are portable to Codex and others.

### F10. Context engineering as a discipline; compaction and handoff practice
**What it is.** HumanLayer's "advanced context engineering" (Dex Horthy): workflow of Research, Plan, Implement, with "frequent intentional compaction" of context into structured artifacts (end goal, approach, completed steps, current failure) and utilisation kept in the "40%-60% range." Context-hungry work (search, flow tracing, logs, big JSON) goes to subagents that return compact output, described as "not trivial." Context priority: correctness, then completeness, then size, then trajectory. Review leverage: a bad research line yields thousands of bad code lines, a bad plan line hundreds, a bad code line one, so humans should review research and plans. Reported by the author: a bug-fix PR approved in a 300k-LOC Rust repo by a non-expert, about 35k LOC in 7 hours on one feature (3 h research and planning, 4 h implementation), about $12k per month on Opus for a team of three; failures include a 7-hour attempt where research did not trace dependencies deeply enough. The page does not use the phrase "dumb zone" (that term comes from talks, not this post). [verified: https://www.humanlayer.com/blog/advanced-context-engineering]
**Anthropic's version** [recalled, not re-read]: "Effective context engineering for AI agents" frames context as a finite attention budget; recommends just-in-time retrieval, compaction, structured note-taking and sub-agent architectures; "find the smallest set of high-signal tokens". Related Anthropic posts that I did not re-open: "Writing effective tools for agents" (fewer, well-described, high-signal tools; evaluate tools with agent transcripts), the Agent Skills design (progressive disclosure: name and description always loaded, body on trigger, scripts and references on demand), and "Code execution with MCP" (agents write code against tool APIs to cut tool-definition and intermediate-result tokens). [recalled]. The skills progressive-disclosure behaviour is confirmed in the Claude Code docs: a skill the model can start itself shows only name and description each session. [verified: best-practices page]
**Evidence caveat.** The 40 to 60% figure is the author's practice, not measured. Anthropic's own docs now say running out of context is "rarely the problem" with 1M windows, though `/clear` between tasks still gives better answers at lower cost. [verified] So the aggressive-compaction doctrine is partly superseded; the research/plan/implement artifact split survives because of human review leverage, not window size.
**Transfer.** v2's handoff files and "fresh-context refuters" align. What v2 lacks is the explicit research document as a reviewable artifact before plan.
**V3 implication.** V3 should keep RESEARCH and PLAN as human-reviewable written artifacts separated by a fresh session when scope is DEEP, because review of those is the cheapest correction point; but it should drop context-window-protection as a stated reason for isolation and instead cite independence and cost. Kernel (wording) plus orchestration.

### F11. Spec-driven development and its critics
**What it is.** Fowler/Thoughtworks's taxonomy: spec-first (spec written before coding a task), spec-anchored (spec kept and evolved), spec-as-source (humans edit only the spec). Kiro: Requirements, Design, Tasks as Markdown, user stories with GIVEN/WHEN/THEN criteria, a "steering" memory (product.md, structure.md, tech.md). GitHub spec-kit: Constitution, Specify, Plan, Tasks with checklists as definition of done. Tessl: spec-anchored/spec-as-source with `@generate`/`@test` tags and "GENERATED FROM SPEC - DO NOT EDIT" headers. [verified: https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html] BMAD, Agent OS and OpenSpec were not read [Gaps].
**Critiques (verified in the same article).** Kiro produced 4 user stories and 16 acceptance criteria for a small bug; spec-kit felt like overkill for a 3 to 5 point feature, created many repetitive files that were tedious to review, duplicated research notes as new specs, and over-applied constitution rules; Tessl showed non-determinism even per file and needed ever more specific specs; brownfield adoption was hard; the author warns spec-as-source may combine model-driven development's inflexibility with LLM non-determinism. "Spec" is overloaded and sometimes just means a detailed prompt.
**Transfer.** v2's "INTENT.md plus acceptance criteria plus per-subtask checks" is spec-first at the task level, which is the part with support. Heavier spec-anchored ceremony is weakly supported.
**V3 implication.** V3 should scale the spec artifact by tier (FAST: none; STANDARD: acceptance criteria and commands in the plan; DEEP: INTENT.md plus plan) and never generate a spec larger than the change, because the only hands-on critique found ceremony cost exceeded benefit on small work. Kernel and intake module. Matches Claude Code's own advice (SPEC.md in one session, build in a fresh one).

### F12. Ralph loop and derivatives
**What it is.** A fixed prompt fed to one agent in an endless loop; each iteration starts with fresh context, picks a task from a spec or plan, implements, and restarts; state lives in files and git. Thoughtworks Radar placed it in **Assess** (April 2026) and says it is no longer on the current radar; it notes the cost (token spend) and that convergence is an expectation, not a guarantee; goose adds cross-model review between iterations. [verified: https://www.thoughtworks.com/radar/techniques/ralph-loop]. Claude Code now has a built-in analogue: `/goal` and the Stop hook with a block cap. [verified]
**Critique.** No controlled evidence found. The Register and Dreamhost pieces exist in search results but were not read [Gaps].
**Transfer.** The fresh-context-per-iteration plus file state pattern is the same mechanism as the Anthropic initializer/coder split. The Stop-hook version is cheaper because it keeps context and adds a deterministic check.
**V3 implication.** V3 should offer an unattended-run mode built on a Stop hook plus ledger (F5) and a hard iteration/cost ceiling, and not a bare infinite loop, because the Stop hook already has a built-in override cap and the Radar flags cost and non-guaranteed convergence. Harness code.

### F13. Superpowers, Beads, Gas Town, and other community orchestration
**Superpowers (Jesse Vincent).** A skills plugin: brainstorming, writing-plans, subagent-driven development with review between tasks, TDD enforcement, packaged as a Claude Code plugin. [recalled; the README could not be fetched; search results confirmed the repo and a plugin page exist at https://github.com/obra/superpowers and https://claude.com/plugins/superpowers]. No measured evaluation found.
**Gas Town and Beads (Steve Yegge).** Beads are small JSON work items in git with id, status, assignee; agent identities are also beads. Roles: Mayor (talks to you, does not code), Polecats (ephemeral single-task workers), Witness and Deacon (supervise and nudge), Refinery (serial merge queue). "Persistent roles, ephemeral sessions"; a new session can "seance" a predecessor. [verified via Maggie Appleton's analysis: https://maggieappleton.com/gastown]. Critiques there: "vibe designed", many overlapping ad hoc concepts, brittle coordination that relies on constant nudging, estimated $2,000 to $5,000 per month, code unreviewed. Appleton judges it speculative design fiction whose patterns will appear in future tools.
**Transfer.** The serial merge queue and persistent task ledger carry over (parallel work needs a single integrator); the role zoo and nudging do not.
**V3 implication.** V3 should include a single-integrator rule for parallel worktrees (one merge queue, rebase and rerun acceptance per merge) and a git-backed task ledger, but no named-role hierarchy beyond lead/builder/verifier, because the role-heavy design is reported brittle and unreviewed. Orchestration.

### F14. Simon Willison, vibe engineering, lethal trifecta
**What it is.** "Agentic engineering" is defined as building software with coding agents that can generate and execute code and iterate without turn-by-turn supervision, practised by professionals amplifying expertise, in contrast to vibe coding. His published patterns include "writing code is cheap now" and red/green TDD (test-first helps agents write more succinct, reliable code with little extra prompting). [verified: https://simonwillison.net/2026/Feb/23/agentic-engineering-patterns/]. The "lethal trifecta" (access to private data, exposure to untrusted content, ability to communicate externally) and the "vibe engineering" post exist at https://simonwillison.net/2025/Oct/7/vibe-engineering/ [title and URL from search; content recalled, not read].
**Transfer.** The trifecta is a precise safety classifier: if a task grants all three capabilities at once, the risk is structurally high regardless of the model's good behaviour. It is a better safety signal than a vague "safety sensitivity" score.
**V3 implication.** V3's CLASSIFY safety check should include the lethal-trifecta test (private data, untrusted input, external egress all present) as an automatic escalation and a hook-enforced network/credential deny, because it is a crisp structural criterion and not a judgement. Kernel (one line) plus harness code.

### F15. Review bottleneck and agent PR volume
**What it is.** Osmani's survey collects: Faros AI (22,000 developers, March 2026) reporting median review duration up 441.5% and PRs merged with zero review up 31.3%; CodeRabbit (470 PRs) reporting AI co-authored changes had about 1.7x more issues; GitClear reporting about 4x raw output but about 12% real productivity gain; Anthropic's Code Review reporting substantive review coverage rising from 16% to 54% with under 1% of findings marked incorrect; a four-tool test where 93.4% of flagged locations were caught by exactly one tool; arXiv papers on agent PRs (about 28% of 33,707 merge almost instantly; reviewer abandonment accounts for 38% of rejected agent PRs). Osmani notes CodeRabbit and Faros sell into this market. [verified: https://addyosmani.com/blog/agentic-code-review/]. Mechanisms recommended: tier review by blast radius, an intake bar for agent PRs (purpose statement, test output, proof of run, bounded diff), cheap triage, small PRs, heterogeneous AI reviewers, scrutiny of test rewrites (mutation testing), strict CI that agents cannot weaken, a decision log on each PR, AI review as sensor and human as merge owner.
**Productivity measurement caveat.** METR's early-2025 RCT found experienced open-source developers 19% slower with AI (CI +2% to +39%); its February 2026 update found late-2025 point estimates of 18% and 4% speedups with intervals including zero and calls the data an "unreliable signal" because of selection effects and task substitution. [verified: https://metr.org/blog/2026-02-24-uplift-update/]
**Critique.** Most numbers are vendor- or advocate-sourced; the arXiv items were quoted by Osmani and not read directly.
**V3 implication.** V3's REPORT step should emit a PR-ready package (purpose, intent link, commands run with outputs, risk tier, decision log) and a hook should refuse to open a PR without it, because the field's review bottleneck is fed by agent PRs lacking proof of execution. Also add a "do not weaken gates" PreToolUse hook (deny edits that delete tests, lower thresholds or skip lint without a human flag). Harness code and the human-briefing module.

### F16. Prompting for the newest models: less scaffolding, literal compliance
**What it is.** Anthropic's Sonnet 5 prompting page: the model "interprets prompts literally and explicitly, particularly at lower effort levels" and does not generalise an instruction from one item to another; state scope explicitly ("every section, not just the first"). Remove progress-update scaffolding ("after every 3 tool calls, summarise") and tool-use nudges unless needed. Conservative review instructions ("only report high-severity") now cause real findings to be dropped, so use a find-everything stage then a separate verification stage. Positive examples beat prohibitions. Front-load the full task, intent and constraints in the first turn for autonomous coding. `xhigh` effort is recommended for the hardest agentic coding; match benchmarks by observed thinking length, not effort name; with thinking off the model uses tools less. [verified: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5]. The Claude Code docs say emphatic wording is over-applied by current models. [verified]. Pages on "Fable 5.1 prompting rules changed" and Opus 5.5 prompting exist in search results (mindstudio.ai, betterstack) but are third-party and unread.
**Transfer.** Literal compliance means any JORDAN rule not stated for a specific case may be dropped, and any rule stated emphatically may be over-applied.
**V3 implication.** V3's kernel should be rewritten in plain, scoped, positive sentences ("do X when Y") with no capitalised mandates, and its reviewer prompts should split "find all" from "verify and rank" stages, because the vendor says both emphasis and conservative filters now misfire. Kernel and module prompts. Evaluate with an A/B in the eval suite.

## Which JORDAN v2 ideas are mainstream, superseded, or missing

**Mainstream (v2 is aligned with the field):**
- Wire the verifier first / give the agent a check to run (Anthropic best practices, Anthropic harness, OpenAI harness, Simon Willison red/green TDD).
- Plan then execute with acceptance criteria and commands per milestone (OpenAI plans.md; Claude Code plan mode and SPEC.md).
- Fresh-context independent review (Claude Code `/code-review`, Cognition, Anthropic evaluator).
- Escalate and ask a human; honest completion with evidence; smallest change.
- Premium lead with cheaper workers; pointer briefs with objective, format, boundaries (Anthropic research system).
- Hooks enforce gates (Anthropic's guidance).
- External state files for long runs (Anthropic, OpenAI).

**Moved past or contradicted:**
- Prompt-simulated pipeline phases (12 phases) as the mechanism: vendor harnesses shrink as models improve and put checks in code.
- Emphatic MANDATORY wording and long maxim lists in the always-on file (vendor says over-applied; instruction-file evidence says cost with little gain).
- Context-window protection as the reason for isolation (Anthropic says rarely binding at 1M tokens; isolation is for independence, parallelism and noisy output).
- Fixed premortem persona counts (4 or 5) with no evidence of benefit; reviewers over-report unless scoped.
- Numerical risk scoring across five axes (no source found supporting this; v2's own review agrees it has not been measured).

**Widely adopted practices v2 lacks:**
1. A structured, tamper-resistant task ledger (feature list JSON with `passes`, `init.sh`, progress file) and an orientation protocol at session start.
2. Ablation and eval discipline for the harness itself (Anthropic removed components model by model).
3. Review-capacity design: PR intake bar, risk-tiered review, heterogeneous reviewers, "do not weaken CI" guard.
4. Drift control: lints with remediation messages, scheduled cleanup agents (OpenAI).
5. Worktree-per-agent parallelism with a single merge integrator; `.worktreeinclude`, `/batch` style fan-out for mechanical changes.
6. Cost and effort control: effort levels per phase, token spend logging, `CLAUDE_CODE_SUBAGENT_MODEL`, cache TTL awareness (agent teams note 5-minute versus 1-hour cache for teammates). Practitioners report fan-out multiplies cost (about 15x in Anthropic's number; about 20x for the full harness on one task).
7. Lethal-trifecta safety test and sandboxing (Willison; Anthropic containment posts, not read).
8. `/goal`-style completion conditions checked by a separate model for unattended runs.
9. Model-specific prompt audit (`/doctor prompt-audit`).

## Contradictions with JORDAN v2

1. **Prompt kernel vs. harness enforcement.** v2's CLAUDE.md is a long mandatory-voiced instruction file. Evidence: the vendor says rule-with-no-exceptions belongs in hooks; ICLR study found LLM-generated context files hurt and human ones help marginally. v2 should be small and mostly enforced.
2. **Fixed 12-phase pipeline vs. shrinking harnesses.** Anthropic's own harness dropped sprints and per-sprint evaluation as the model improved. v2 presents its phases as constant.
3. **"Subagents protect context"** (an implied v2 rationale) is on Anthropic's obsolete list. Fresh reviewers help for independence, not for window space.
4. **Parallel builders.** v2's cheaper models "build and sweep"; Cognition and Anthropic both say parallel writers conflict. This holds only with strict fences and a single integrator.
5. **Self-escalation by cheap models.** Cognition found weak primaries cannot judge when to escalate; v2 leans on the model's own escalate-don't-bury rule. Triggers must be mechanical.
6. **Verifier prompts that "find problems"** over-report; Claude Code docs and the Sonnet 5 guide both say to scope them and separate find from rank.
7. **Instruction to "classify one tier lower and promote on surprise"** is untested; the Anthropic effort guidance suggests effort is a continuous control (low/medium/high/xhigh/max), which is a simpler routing knob than three tiers. Not a proven contradiction.

## Hype and weak evidence

- **Gas Town and swarms**: unreviewed code, brittle nudging, high cost; its own critics call it design fiction. Cognition calls unstructured swarms "mostly a distraction."
- **Spec-as-source and heavy spec-driven toolchains**: only hands-on, anecdotal critique found; the vendors' own claims are untested.
- **Ralph loop**: Assess ring, dropped from the current radar, no controlled results found.
- **Vendor productivity statistics** (Faros, CodeRabbit, GitClear, Devin Review's bugs per PR, OpenAI's one-tenth-of-the-time estimate, HumanLayer's 35k LOC in 7 hours): all self-reported or sourced from sellers in the market. METR's RCT shows developers' own speed estimates can be wrong, and its 2026 update is explicitly inconclusive.
- **"40 to 60% context utilisation" and the "dumb zone"**: practitioner rule of thumb with no measurement; the vendor now says running out of context is rare.
- **Premium multi-agent gains** (90.2%): internal eval, with token spend a major confound.
- **Agent teams**: documented as experimental with real limits; most community write-ups are tutorials, not evaluations.
